# Безопасность и резервное копирование

## Роли и права доступа

В базе четыре роли: `shop_admin`, `shop_manager`, `shop_operator`, `shop_readonly`. Права выдаются по принципу минимальных привилегий — каждая роль получает только то, что необходимо для её обязанностей. Администратор управляет базой, менеджер работает с товарами и заказами, оператор меняет только заказы и доставки, а readonly может только читать. Это ограничивает ущерб от компрометации учётной записи обычного сотрудника.

## GRANT и REVOKE

Привилегии на таблицы и последовательности выдаются через `GRANT` и отзываются через `REVOKE`. Например, оператору нельзя удалять заказы, поэтому право `DELETE` на таблицу `orders` для него отозвано. Readonly-роль не получает никаких прав на изменение данных — только `SELECT`. Список всех granted и revoked прав находится в `sql/05-roles-and-permissions.sql`.

## Принцип минимальных привилегий

Каждая роль ограничена в действиях. Менеджер не может изменять структуру таблиц, оператор не может создавать новые заказы, а пользователь только для чтения не может вообще ничего менять. Разделение прав предотвращает случайные и умышленные изменения данных сотрудниками, которым это не требуется по службе.

## Защита соединения

Между приложением и PostgreSQL должен использоваться SSL/TLS. На стороне сервера в `postgresql.conf` включается поддержка SSL:

```ini
ssl = on
ssl_cert_file = '/etc/postgresql/server.crt'
ssl_key_file = '/etc/postgresql/server.key'
```

Клиентское подключение с обязательным шифрованием:

```bash
psql "host=localhost port=5432 dbname=shopdb user=shop_admin sslmode=require"
```

## Параметры подключения

Пароли и параметры подключения не хранятся в исходном коде и не попадают в репозиторий. Они задаются через переменные окружения `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGPASSWORD`. Скрипты `scripts/backup.sh` и `scripts/restore.sh` берут эти значения из окружения, поэтому секреты нежестко закодированы в скрипты.

## Целостность данных

Ссылочная целостность обеспечивается первичными и внешними ключами: нельзя создать заказ несуществующему клиенту или позицию без заказа. UNIQUE защищает от дублей артикулов, почт и имён входа. NOT NULL гарантирует наличие обязательных полей. CHECK закрепляет бизнес-правила на уровне базы: неотрицательные цены, остатки и стоимость доставки, положительное количество товара в позиции, допустимые наборы статусов.

## Транзакции

Операции, затрагивающие несколько таблиц, должны выполняться внутри транзакции. Например, оформление заказа с созданием позиций, уменьшением остатков на складе и созданием платежа оборачивается в `BEGIN ... COMMIT`. Если любая операция не удаётся, транзакция откатывается (`ROLLBACK`), и база остаётся в согласованном состоянии.

## Резервное копирование

Резервные копии делаются утилитой `pg_dump`, которая создаёт логическую копию базы в виде SQL-скрипта. Такой бэкап содержит команды создания объектов и вставки данных, поэтому его можно восстановить на любом сервере PostgreSQL той же или более новой версии. Копии создаются по расписанию, например ежедневно ночью, и хранятся не менее семи тридцати последних экземпляров. Периодически, раз в месяц, стоит выполнять тестовое восстановление на отдельном сервере, чтобы убедиться, что бэкап рабочий и данные целы.

## Восстановление

Восстановление из обычного SQL-дампа делается через `psql`. Если бэкап сделан в произвольном формате, используется `pg_restore`. В проекте скрипт `scripts/restore.sh` принимает путь к файлу бэкапа и восстанавливает базу, используя параметры подключения из переменных окружения.
