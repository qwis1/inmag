# Бизнес-правила

Ниже приведены бизнес-правила интернет-магазина. Они отражают реальные ограничения работы магазина и, где это возможно, реализованы на уровне базы данных через ограничения PostgreSQL.

1. Артикул товара (SKU) должен быть уникальным. Два разных товара не могут иметь одинаковый артикул, так как он используется для учёта на складе и поиска. Реализовано через `UNIQUE` на `products.sku`.

2. Электронная почта клиента должна быть уникальной. Один адрес почты может быть зарегистрирован только один раз. Реализовано через `UNIQUE` на `customers.email`.

3. Имя входа сотрудника (username) должно быть уникальным. Одно имя не может принадлежать нескольким пользователям системы. Реализовано через `UNIQUE` на `users.username`.

4. Цена товара не может быть отрицательной. Стоимость единицы товара должна быть больше или равна нулю. Реализовано через `CHECK (price >= 0)` на `products.price`.

5. Цена за единицу в позиции заказа не может быть отрицательной. Реализовано через `CHECK (unit_price >= 0)` на `order_items.unit_price`.

6. Количество товара в позиции заказа должно быть больше нуля. Нельзя оформить заказ на ноль или отрицательное количество единиц. Реализовано через `CHECK (quantity > 0)` на `order_items.quantity`.

7. Остаток товара на складе не может быть отрицательным. При списке товара остаток не уходит в минус. Реализовано через `CHECK (stock_quantity >= 0)` на `products.stock_quantity`.

8. Общая сумма заказа не может быть отрицательной. Реализовано через `CHECK (total_amount >= 0)` на `orders.total_amount`.

9. Сумма платежа не может быть отрицательной. Реализовано через `CHECK (amount >= 0)` на `payments.amount`.

10. Стоимость доставки не может быть отрицательной. Реализовано через `CHECK (delivery_cost >= 0)` на `deliveries.delivery_cost`.

11. Заказ должен принадлежать одному конкретному клиенту. Каждый заказ привязан к существующему клиенту интернет-магазина. Реализовано через внешний ключ `orders.customer_id → customers.customer_id`.

12. Позиция заказа должна ссылаться на существующий заказ и существующий товар. Реализовано через внешние ключи `order_items.order_id → orders.order_id` и `order_items.product_id → products.product_id`.

13. Платеж должен относиться к существующему заказу. Каждый платеж привязан к одному заказу. Реализовано через внешний ключ `payments.order_id → orders.order_id`.

14. Доставка должна относиться к существующему заказу. Каждая доставка привязана к одному заказу. Реализовано через внешний ключ `deliveries.order_id → orders.order_id`.

15. Каждый пользователь системы должен иметь ровно одну роль. Роль определяет набор прав пользователя и не может быть отсутствующей. Реализовано через `NOT NULL` на `users.role_id` и внешний ключ `users.role_id → roles.role_id`.

16. Товар должен принадлежать к одной существующей категории. Реализовано через `NOT NULL` на `products.category_id` и внешний ключ `products.category_id → categories.category_id`.

17. Статус заказа может принимать только допустимые значения: создан, ожидает оплаты, оплачен, в обработке, отправлен, доставлен, отменён. Реализовано через `CHECK` на `orders.status`.

18. Статус платежа может быть: ожидание, успешно, отменено, возвращено. Платеж считается завершённым только со статусом «успешно». Реализовано через `CHECK` на `payments.status`.

19. Статус доставки может быть: оформлена, в пути, доставлена, отменена. Реализовано через `CHECK` на `deliveries.status`.

20. К одному заказу относится не более одного платежа и не более одной доставки. Это гарантирует, что заказ не дублируется в платежах или доставках. Реализовано через `UNIQUE` на `payments.order_id` и `deliveries.order_id`.

21. Заказ с конечным статусом (доставлен или отменён) не должен быть изменён повторно. Это правило на уровне приложения и триггеров базы данных, которые блокируют повторную правку завершённых заказов.

22. При удалении заказа его позиции, платеж и доставка удаляются автоматически, так как они не имеют смысла без самого заказа. Реализовано через `ON DELETE CASCADE` на зависимых таблицах.

23. Нельзя удалить категорию, если в ней остались товары, и нельзя удалить товар, если он фигурирует в оформленных заказах. Это предотвращает потерю истории. Реализовано через `ON DELETE RESTRICT`.

24. Пароли сотрудников не хранятся в открытом виде и не попадают в репозиторий. Учётные данные задаются через переменные окружения или отдельно при создании пользователя.
